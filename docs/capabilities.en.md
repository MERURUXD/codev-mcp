# Capabilities and Limits

[中文](capabilities.md)

This list describes the tools, the standalone command-line entry points and their boundaries. The real backend needs Windows, CODE V 10.2 and a working license; this experimental release does not guarantee that every lens or failure path completes. The simulated backend is for protocol and workflow demonstrations only; its numbers must not be used for optical conclusions.

## 1. Tool capabilities

| Tool | Capability |
| --- | --- |
| `get_status` | Backend type, CODE V version, session and lens state, current task, capability list |
| `open_lens` | Opens a working copy of a `.len` file and returns the full lens data |
| `create_lens` | Only in an empty session: creates a single-zoom lens of ordinary spherical surfaces from a typed specification; optional `image_solve="pim"` adds a paraxial image solve to the thickness of the last ordinary surface (the requested thickness is only a starting value); publishes revision 0 after a full read-back and a save/reopen |
| `get_lens` | Surface numbers/roles/stop, radii and thicknesses (with infinity flags), glass names and catalogs, units, native system aperture type and value, explicit clear apertures/obscurations, effective maximum aperture, fields (including vignetting factors `vux/vlx/vuy/vly`), wavelengths, zoom positions |
| `update_lens` | Surface radius/thickness/glass, field X/Y angles and weights, field vignetting factors `vux/vlx/vuy/vly` (-0.99 to 0.99), wavelength values/weights/reference wavelength; on single-zoom lenses, the existing system aperture value and a single centered circular explicit clear aperture radius; one restore point per batch; read-back verification; the whole batch either takes effect or is rolled back; a flat (infinite radius) surface can be given a finite radius directly (only radius edits may change the infinity flag; any other edit that changes it rolls the batch back), and thickness still cannot switch between infinite and finite. `field_set` replaces the whole angle field set of a single-zoom lens (count, angles, weights, vignetting factors; separate transaction, not mixed with `edits`; see [field sets](field-set-and-seq-import.en.md)) |
| `edit_lens_structure` | Only for simple spherical lenses created by this service: batch insert/delete of ordinary surfaces and setting the stop; step-by-step surface number mapping and full read-back verification; a failure restores the whole batch |
| `run_analysis` | First-order data, spot diagram, diffraction sine-wave MTF, WAV RMS/Strehl at the currently saved focus; `native_plot` is drawn by CODE V itself and exported as PNG (five plot types) |
| `get_analysis` | Task state, structured numbers, images (returned as MCP image content while the result files are kept); native plots also carry the `.PLT` path and size |
| `cancel_analysis` | Requests cancellation and distinguishes "requested" from "confirmed stopped"; applies to asynchronous tasks (spot diagram, native plot); native plots also close the plot file CODE V has open |
| `save_lens_as` | Saves to a new file; refuses to overwrite the source file or an existing file |
| `close_session` | Releases the session created by this service and cleans up that session's processes |

The `--config` option of the standalone scan CLI can select first-order, spot, MTF and WAV analyses on a single-zoom lens with a confirmed fixed focus. It produces per-sample metrics, condition-bound curves and per-requirement status, and explicitly saves a candidate and recomputes it after reopening in a separate session. It adds no public MCP tool and does not refocus automatically or accept candidates.

Common conventions: every result carries `source` (`codev` or `simulated`); every failure returns a structured error (`parameter`, `not_ready`, `computation_failed`, `session_invalid`, `unsupported`, `not_found`, `internal`).

The simulated backend uses its own synthetic model; the branch selected by a `dbgauss` file name also returns synthetic data. First-order constants are test data; the simulated backend does not parse real `.len` files and proves nothing about physical performance.

### Initial/final lens comparison

Beyond the public tools there is a command-line orchestration entry point, `python -m codev_mcp.compare`, which reuses the tools above to build an initial/final lens analysis comparison package without adding any COM command entry. Supported scope, the default strict compatibility check, the field-weight difference option and the failure rules are in the [comparison workflow](comparison-workflow.en.md). The simulated workflow only checks the protocol and the package layout; it does not parse real lenses.

The comparison entry point can explicitly choose analysis kinds, fields, MTF frequencies and spot grid settings, and `python -m codev_mcp.batch` produces pairwise batch reports. A batch only summarizes complete numeric results from the same request and the same actual settings, and gives no ranking across conditions. Explicit multi-zoom orchestration covers first-order, spot and numeric MTF only; WAV and native plots remain single-zoom. See the [two-lens workflow](comparison-workflow.en.md) and the [batch workflow](batch-workflow.en.md).

The standalone [local glass catalog query CLI](glass-catalog.en.md) uses CODE V's native `GLD` to query, read-only, the installed catalogs, exact glass names and the listed refractive index at given wavelengths. It adds no MCP tool and does not modify user lenses. Two-lens comparison records run time and COM call counts and supports explicit bounded reuse with `--max-analyses-per-session`; by default each item gets its own session. See the [performance workflow](performance-workflow.en.md).

The standalone [fixed-grid parameter scan CLI](parameter-scan.en.md) modifies an existing radius or thickness of a single-zoom lens. Each value opens its own session from the same baseline snapshot and reuses the `update_lens` transaction and first-order analysis; failed samples are recorded individually, there is no implicit optimization, and no MCP tool is added.

The typed specification, constraints and staged behavior of controlled AUT are in [Multi-variable constraints and staged AUT](#multi-variable-constraints-and-staged-aut).

### Design specification evaluation and judgement

The comparison entry point supports a single-lens mode with `--lens` and `--spec`: the [design specification](design/design-spec.en.md) decides the analysis kinds, structured MTF frequencies and spot grid. The package additionally stores the native `LIS` text, a copy of the specification and a map between plots and data, and writes per-requirement judgements to `evaluation.json`. Judgement covers the system definition (aperture, field, wavelength, glass catalog), first-order data (`OAL` excludes the image distance), MTF, spot, WAV, the maximum absolute value of the FIE reference-wavelength distortion table, center/edge thicknesses of glass and air, and the explicitly selected Maréchal and Airy disk presets. Edge thickness and Airy disk diameter are values the service computes from CODE V data and are marked as such; a print precision that straddles the threshold, missing data, a simulated source or a threshold still to be filled in always gives unknown. No MCP tool is added, no new CODE V command is sent and the lens is not modified; the native MTF plot still fixes `MFR 100; IFR 10`.

### Nearby glass candidates

The standalone read-only CLI `python -m codev_mcp.glass_near` takes a reference glass (`name_catalog`) or nd/νd as the basis and lists candidates from the `GLI` listing of the installed catalogs named by the caller, sorted by √((Δnd/0.01)²+(Δνd/1)²). νd is computed from the printed refractive indices and is reported with its print-precision interval. No catalog is preset and no glass is replaced. See [glass catalog queries](glass-catalog.en.md#nearby-glass-candidates).

### Starting-point scaling

The standalone CLI `python -m codev_mcp.scale` uses the public MCP tools to scale, by a target EFL or a factor, an angle-field lens that is single-zoom, has only a `PIM` solve, no pickups and no special surfaces. Finite radii, non-solved thicknesses, finite object distance, EPD and a single centered circular clear aperture are multiplied by the same factor in one `update_lens` transaction; the `PIM` image distance is re-solved by CODE V and reported item by item. After saving, the lens is reopened and recomputed in a separate session; an EFL relative deviation above 1e-9 fails the run and writes no output. Each run leaves an [execution record](design/execution-record.en.md) listing the equivalent commands actually sent.

### Multi-variable constraints and staged AUT

[Controlled AUT](controlled-aut.en.md) uses a typed specification: stages run one after another, and each stage can set existing spherical radius/thickness variables (optionally with bounds), whitelisted specific constraints (`EFL`, `EFY`, `OAL`, `IMD`, `DIY`, `CT`, `ET`), general thickness constraints (`MXT`, `MNT`, `MNE`, `MNA`, `MAE`), error function parameters (`MXC`, `MNC`, `TAR`, `IMP`, `DEL`, `WTA`) and field/wavelength weight changes. `PIM` and solves/pickups that do not control a requested variable may remain and are listed item by item. AUT output is redirected with `OUT` to a service file and parsed; specific constraints are judged one by one against the final table, general constraints are rechecked by the service against the thicknesses, and CODE V frozen-thickness warnings are listed. Native variable control codes are restored after the run. Each stage saves and verifies an intermediate candidate, so a failure in a later stage keeps the earlier candidates; a candidate with unmet constraints can be accepted but is clearly marked. Field angles, weights and vignetting factors can be changed, typed, before a stage; `field_ramp` expands into stages that each continue from the previous candidate, and only the final candidate can be explicitly accepted. Variable starting values may lie on or outside a bound, which the stage record notes; vignetting factors are not AUT variables. A surface that starts flat (infinite radius) can be a `radius` variable; a flat start carries no radius bounds, and variable records carry `before_infinite`/`after_infinite`.

### Typed edits, readable sequence export and design records

- `python -m codev_mcp.edit`: sends one `update_lens` transaction to a copy of a single-zoom lens from a `lens_edits` file (public `ParameterEdit` records, 1 to 100 entries), for example a glass swap; reads back, saves as, reopens and recomputes in a separate session, and does not write the input. The equivalent commands in the execution record are rebuilt in the backend's format.
- `python -m codev_mcp.export_seq`: sends only `RES`/`WRL` to export the lens as a new readable `.seq`, refusing to overwrite. A lens after AUT carries `DER VAL` derivative increment lines.
- `python -m codev_mcp.seq_import`: parses a `.seq` against a command whitelist into typed requests (`create_lens` including `PIM`, `update_lens` field set and wavelength edits). The service builds the commands and never executes the sequence or `IN`; any line outside the whitelist rejects the whole file and is listed line by line, and metadata and variable markers are listed as "not imported". After import, read-back values and `LIS` are checked item by item; after saving, the lens is reopened and rechecked in a separate session, and it can be compared item by item with a reference `.len`.
- `python -m codev_mcp.schemes`: runs several schemes in a batch from the same baseline (typed changes: glass swap, vignetting or field set, each optionally with its own AUT specification) → staged AUT → candidate. It runs serially by default; `--jobs N` (1 to 8) runs N schemes at once, each in its own worker process and session (session start is queued by a machine-wide mutex, and the shared `cvcomsvr.exe` is not ended by any single session). A failed scheme is recorded and the run continues (but if it leaves a process that cannot be confirmed, no new scheme is started). It summarizes error function, WAV, first-order data and optional specification judgements, and lists comparable and non-comparable quantities (when vignetting, field weights, wavelength weights or error function settings differ, error function and WAV cannot be compared directly, and the groups are explained). `--screen-cycles N --finalists K` first screens by error function within comparable groups, then runs at most K finalists per group in full and independently from the original baseline; screening keeps stage/constraint and WAV diagnostics, and the final recommendation uses full-stage results only. Cleanup decisions read structured state; when diagnostics time out and no leftover is finally confirmed, later schemes continue. It only recommends and never accepts candidates. See [scheme comparison](scheme-comparison.en.md).
- `python -m codev_mcp.deliver`: organizes evaluation packages and AUT runs into report material: initial/final paired plots (`init-*`, `final-*`, including native `.PLT`), `LIS`, raw WAV text, optimization macros (the verbatim command block and an equivalent hand-written macro trimmed from the record; `--setup` can put the equivalent commands of glass swaps, scaling and `.seq` import in front), raw AUT output and summary, and a material index. It only copies and checks hashes, does not recompute or send commands, and refuses to overwrite; when the initial lens cannot be fully traced it gives only the plots actually produced and lists the reasons item by item. See [deliverables](deliverable.en.md).
- `python -m codev_mcp.fieldset`: computes angles from a maximum field angle and relative fields, normalized by image height (tan) by default with the convention stated, and outputs a `field_set` usable directly with `update_lens`; it only computes and does not connect to CODE V.
- The edit file of `python -m codev_mcp.edit` can use `field_set` instead (either it or `edits`). See [field sets, image-height normalization and `.seq` import](field-set-and-seq-import.en.md).
- `python -m codev_mcp.walkthrough`: reads the [execution records](design/execution-record.en.md) of each CLI and the design specification and produces a design record in Chinese. It covers goals and requirements, materials, ordered steps with reproducible commands, the plot list, measured data and judgements, and caveats. It only renders numbers from the records, writes "missing" (缺失) where data is absent, writes no report prose, copies no images and refuses to overwrite.

## 2. Explicitly not supported

- Automatic optimization, tolerancing and sensitivity analysis in the public MCP tools. AUT runs only through the standalone [controlled candidate command line](controlled-aut.en.md) from a typed specification; `run_analysis` never modifies the lens. AUT does not support multi-zoom, glass variables, aspheres, image defocus variables, `IMC`/`TT`/ray constraints or user-defined error functions
- Adding or removing surfaces, or changing surface types or special surface shapes, in arbitrary existing lenses; structural editing is open only to the restricted newly created lenses above
- Executing arbitrary commands or macros: the service only sends commands it builds itself, with parameters checked against whitelists
- Remote access: local stdio only
- Controlling a CODE V GUI the user has opened (the service only creates and uses its own windowless session)
- MTF of afocal systems (returns `unsupported`)
- Geometric MTF (the first release only does diffraction sine-wave MTF)
- Switching the system aperture type; converting an automatic aperture to an explicit one; editing an explicit circular aperture that is kept but inactive under `CA NO`; obscuration, non-circular, decentered, rotated, OR/compound and multi-zoom aperture edits. NA/NAO writes are conservatively limited to below 1, even though ≥1 can be meaningful in high-index media. The old names `semi_aperture` and `clear_aperture` are ambiguous and remain read-only
- Spot diagrams for several fields in one task (one field per task)

## 3. Limits and caveats

1. **Long-session stability**: do not treat a single CODE V session as a service that runs indefinitely. Call overhead varies with the lens and sampling settings; long continuous work is best split into segments, re-establishing the session when needed. `--max-analyses-per-session` is a bounded orchestration option, not a fixed safe call threshold of CODE V.
2. **One analysis at a time**: while an analysis runs, `open_lens`, `get_lens`, `update_lens`, `save_lens_as` and a second `run_analysis` are refused.
3. **The asynchronous tasks are spot diagram and native plot**: both are submitted asynchronously with `AsyncCommand`, need polling with `get_analysis`, and can be cancelled with `cancel_analysis` while running. First-order, MTF and WAV run synchronously inside `run_analysis` and return only when done, so they cannot be cancelled; meanwhile other calls just wait in the client queue, and once the per-call timeout (660 seconds by default, a little longer than the 600-second limit of one CODE V command, adjustable with `--timeout`) is exceeded the client terminates the worker process; the next tool call rebuilds the worker automatically, and the new worker first stops the CODE V processes the old one recorded, but does not restore the lens that was open. A call that has to start a CODE V session (the first lens operation, or a rebuild after the engine exited) gets an additional start budget (the start lock wait plus the limits of every start retry), so a first start of about two minutes does not time out. For analyses expected to take long, raise the limit with `--timeout` first or submit them in batches.
4. **Multi-zoom lenses**: edits must give `zoom_position`; if the parameter itself is not zoomed, the service changes the shared value and says so in `warnings`.
5. **Solves and pickups**: parameters controlled by a solve or pickup are refused; if the solve probe itself fails, the edit is still attempted and `warnings` says so, with read-back verification as the safety net. Even if CODE V silently ignores an edit, read-back verification catches it and rolls the batch back.
6. **Infinite values**: a radius ≥1e17 or a thickness ≥1e10 is treated as infinite; CODE V may represent infinity as `0.1E+19` and about `9.9e11`.
7. **Numeric precision**: first-order data comes from string evaluation, about 16 significant digits; back/front focal distances and paraxial image height come from printed listings and have print precision only, which is marked separately.
8. **Spot diagram conventions**: native SPO reports diameters; the service converts them to radii and sets `size_is_radius=true`. `statistics_sample_count` is the number of rays in the native statistics and `plot_sample_count` the number of rays in the plotting grid. Plot coordinates are traced with RAYTRA (aperture checking must be on, otherwise obscured rays return invalid coordinates). Grid launch points use real ray aiming: for each wavelength, 17 `RAYRSI` rays (relative pupil, reading `(X S1)`, `(Y S1)`, `(Z S1)` and subtracting Z times the object-side direction tangent to convert to the first tangent plane) are fitted with a cubic polynomial, and the grid is then traced with `RAYTRA`; the relative pupil is scaled by that field's vignetting factors, so it traces the same pupil as native SPO. A warning is given when the mapping deviates from the calibration rays by more than 0.5% of the pupil radius; plotting-grid rays blocked by apertures are listed and not drawn; with fewer than 10 calibration rays the spot task fails. The plot is centered on the grid centroid; the gray circle is the native 100% radius, and the green circle is the Airy disk radius 1.22λF/# computed by the service (reference wavelength and infinite-conjugate F/#; not drawn for finite object distances; not a CODE V result). The plotting grid samples differently from native SPO, so the plotting-grid RMS must not replace the native statistics. The native statistics are read by the field number SPO prints; when the output lacks the requested field the task fails with `computation_failed` instead of reporting another field. `ray_grid` takes 1 to 101; MTF takes at most 101 finite, nonnegative frequencies; MTF always reports the tangential (0°) and sagittal (90°) curves, so `azimuth` may only be omitted or 0.
9. **Output truncation**: when output fills the text buffer, the task is marked `output_truncated=true` and warnings say so; missing statistics are treated as a failure and no partial result is given.
10. **Session invalidation**: when a rollback fails or a stop is not confirmed, the session is marked invalid and later writes are refused.

11. **Aperture read and edit boundaries**: `aperture.kind` keeps the native `epd`, `fno`, `na`, `nao`, and `value` is the value of that type at the actual zoom position; only EPD uses lens length units. `derived_epd` is a separately marked derived value. The surface `semi_aperture` comes from `GetMaxAperture` and is the effective maximum semi-aperture computed by CODE V, not an explicit `CIR` definition. Explicit definitions are kept in `surfaces[].apertures` with radii in lens length units; multi-zoom surface values are read from the `ZOOM DATA` of `LIS`, and when that read is incomplete `aperture_data_complete=false` and writes are blocked. Aperture edits are only allowed on single-zoom lenses, either keeping the system aperture type and changing only the value, or, when CA uses user-defined apertures, changing the radius of the surface's single centered circular clear aperture; no explicit definition, `CA NO`, obscurations or any compound combination are refused before writing.

12. **Trusted lens state and checkpoints**: `update_lens` reports success only after the whole batch has passed read-back verification and the working copy has been written to an independent checkpoint (save → reload → compare item by item). Checkpoints live in `<working directory>/checkpoints/<backend instance UUID>/<lens UUID>/revision-00NNNN.len`, and the successful revision is pointed to by `current.json` in the same directory; revision files are never overwritten. The checkpoint format is defined by [`CHECKPOINT_FORMAT_VERSION`](../src/codev_mcp/checkpoints.py); format 6 includes the native system aperture type, its value at each zoom position, the CA usage mode, per-zoom surface apertures, native aperture commands, the solve/pickup commands from `LIS`, the `CCY/THC/GLC` variable control codes, and per-field, per-zoom vignetting factors `VUX/VLX/VUY/VLY`. A missing relation section or variable control column rejects the snapshot, and so does a mismatch between the zoom position 1 vignetting factors and the values printed in the `LIS` specification section (five decimals; rows not printed count as all zeros), so that an unrecognized database item cannot echo a previous result. Versions 1 to 5 refuse automatic recovery and ask you to reopen the source lens; old files are not rewritten. Vignetting factors can be written per field and per zoom position with `update_lens` (`VUX/VLX/VUY/VLY Fn`, limited to -0.99 to 0.99) and are read back, cross-checked against `LIS` and written to the checkpoint like other parameters; if vignetting factors change while other parameters are edited, the batch is rolled back. The snapshot still does not fully cover special surface shapes, decenters, coatings and similar attributes, which is why structural writes are only allowed on simple spherical lenses created by this service. After the engine exits, the next lens operation rebuilds the session and restores and verifies the revision `current.json` points to; if recovery cannot be confirmed, the session is marked invalid.

13. **Solve coupling**: a batch requires that "only the requested parameters change", but CODE V re-derives solve-controlled parameters (for example the image-space gap controlled by `PIM` changes with the gaps in front of it). Such coupling is accepted only when the service has actually detected that the parameter is solve-controlled, and each one is listed in `warnings`; changes with no solve explanation still roll the batch back.
14. **Process cleanup scope**: only CODE V processes recorded by this service are cleaned up; sessions the user started are not affected.
15. **Random engine crashes**: the windowless CODE V engine can crash at random during start-up (`0x40000015` or `c0000005`) and stop on an "Application Error" dialog; the COM server is still alive, so later calls block forever. The service has three safeguards (see section 6.4 of the [installation guide](install.en.md#64-an-application-error-dialog-appears-and-every-call-hangs)): a start-up watchdog terminates an engine with no threads as soon as it sees one (the dialog disappears with it, no manual click needed); session start is retried up to 4 times; when a running engine dies, the next call discards the dead session, rebuilds it, and restores and verifies the lens from the latest successful checkpoint. The rebuild is transparent; an analysis task that was running is marked `failed`, its `error` records `session_invalid` and the reason for the interruption, its result files are kept, and it must be resubmitted. Historical analysis results are labeled with the lens and revision they belong to (`history_only=true` on the task, and `get_status.details` gives `analysis_lens_id` and `analysis_history_only`), keep the real `source=codev`, and never pose as results for the current lens; an engine exit does not clear results that were already completed.

16. **Native plot export**: `run_analysis` supports `kind=native_plot`, which requires `options.plot_type` (`layout` maps to `VIE;LAB NO;GO`, `spot` to `SPO;AIR YES;GO` (overlaying the Airy disk circle computed from the actual ray F-number and the reference wavelength), `mtf` to `MTF;MFR 100;IFR 10;GO`, `ray_aberration` to `RIM;GO`, `field_aberration` to `FIE;LSA;GO`). The service accepts no output path: the plot file and PNG are both written in the service result directory, with names generated by the service that include a unique random part, and existing files are never overwritten. The first release supports PNG only and also keeps the raw `.PLT` CODE V writes; there is no choice of TIF/RAS or other formats, no reading of a CODE V GUI the user has open, and no screenshots or desktop automation. It faithfully draws every field and wavelength enabled in the lens, so it accepts no filter parameters such as `field_numbers`, `wavelength_numbers`, `ray_grid`, `frequencies`, `azimuth` or `mtf_type` (passing one returns `parameter`); the first release supports single-zoom lenses only, and multi-zoom returns `unsupported`. The polling wrap-up order is fixed as `GetCommandOutput` → `GRA T` → check non-empty `.PLT` → `GCV PNG` → check PNG; when `Wait()` reports completion but `IsExecutingCommand()` is still true, it does not wrap up early. PNG checking walks the whole chunk list, verifies each CRC, requires an empty `IEND` at the end with no trailing data, and decompresses the pixel data as a complete zlib stream, so an image with "a valid signature and IHDR but a truncated file" is not taken as valid. Command errors, empty output, command output truncated by the text buffer, a missing or empty `.PLT`, a failed conversion and an incomplete or undecodable PNG all return `computation_failed` (on truncation the files already written are kept for diagnosis but do not count as a complete result); if `GRA T` cannot be confirmed, the session is marked invalid. When polling itself fails (`Wait`, `IsExecutingCommand` or `GetCommandOutput` raises), the service first sends `StopCommand` and confirms the stop, then `GRA T` to restore graphics output, and only then reports the failure; if the stop or restore cannot be confirmed the session is invalid, and the task still ends in a final state instead of staying `RUNNING`. File access errors (for example the converted PNG cannot be read back) are likewise turned into a structured `computation_failed` that ends the task, and files already written stay in the result directory. CODE V truncates the whole filespec of a plot file to 80 characters and appends `.PLT` only if there is still room after truncation, so the service limits the file name length by the space left after the result directory path and reports an error when there is not enough room instead of generating a name that would be truncated; if CODE V still writes a plot file without an extension, the service adds `.PLT` before conversion (only inside the result directory, and without overwriting existing files).

17. **WAV wavefront analysis**: `kind=wavefront` supports single-zoom lenses only, with all fields and wavelengths, fixed `NRD=20`, and explicitly runs `NOM` at the currently saved focus; it does not run `RFO`, which would modify the image thickness. Per-field and composite RMS, Strehl and actual ray counts all come from CODE V native text, with RMS in waves; native X/Y field angles must match the lens row by row. The backend compares verifiable lens snapshots before and after WAV; if a change is found or read-back cannot be confirmed, the task fails, the session is invalidated and later writes are refused. Strehl is the approximation CODE V prints and can be 0 for large RMS. The lens reference wavelength and the equivalent wavelength of a multi-wavelength RMS are not the same field; native text does not provide the latter, so the result leaves it empty instead of substituting the reference wavelength. Best individual/common focus and defocus scans are not implemented yet. WAV runs synchronously and cannot be cancelled midway. At large fields `rays_traced` is lower than on axis because part of the fixed exit pupil grid is blocked by the stop surface and default apertures, not because tracing failed; per-field RMS is over the part of the pupil that passes the apertures, and composite RMS is weighted by each field's ray count, so schemes with clearly different ray counts cannot be compared by RMS directly. The `compare` and `schemes` reports show the accepted pupil ratio alongside, mark differences above 3 percentage points as "pupil differs", and show the composite RMS without ray-count weighting next to it; the result fields of the public tool `run_analysis` are unchanged. AUT's optimization ray grid is not affected by apertures and drops no rays, so the pupil it evaluates differs from WAV.

`FAP` is not on the controlled AUT specification whitelist. It rewrites vignetting and lets the normalized pupil scale change; a WAV ray count close to the on-axis count does not prove that the pupil size was kept or that AUT and WAV are fully aligned.

18. **Installation method and CLI working directory**: the MCP service takes its working directory from `--working-directory`, which also works with a wheel install. The engine working directory of the standalone command-line tools is derived from the package install location and is not affected by `--output-dir`, so use these tools after an editable install in the repository root as described in the [installation guide](install.en.md). A working directory serves one session at a time: a session holds the directory exclusively from start to stop (lock file `codev-mcp-session.lock`, released by the operating system when the holding process exits). Another service instance starting a session in the same directory gets `not_ready` (`details.reason` is `working_directory_in_use`, `details.holder` is the holder's PID); it does not clean up the recovery files or process records in that directory and does not retry within that call. The refused service does not become invalid, and calling again after the directory is released starts the session. When several MCP clients (for example several conversations open at once) each start a service, give each one a different working directory with `--working-directory` or `CODEV_MCP_WORKDIR`; command-line tools use their own engine directory on each run and are not affected.
